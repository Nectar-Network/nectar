**Annotation — the VLT-2 `NoDraw` guard and its consequence.**
`return_proceeds` now rejects any caller with no outstanding draw
(`lib.rs:311-315`, `NoDraw` = 13). This kills the donation-as-profit path the
old code allowed — but it also means **float-funded bad-debt proceeds cannot
be credited to depositors** (`drawn == 0` by construction). Bad-debt profit
therefore accrues to the operator under today's contracts. That is a
deliberate, documented trade (FACTS.md Decisions, AMENDED 2026-08-11), not an
oversight; crediting depositors needs a new registration-gated entry point (a
Tranche 3 candidate).

## Deliverable 3 — Blend adapter: auction integration

**Verdict: PASS on the delivered scope — which is narrower and differently
shaped than the spec's literal wording.** The spec was written before the
mechanics were verified from Blend source; every divergence below was forced
by verified on-chain behavior (docs/FACTS.md), with live evidence.

**Annotation — "implement all Blend auction types" (spec's literal wording).**
The three auction kinds move DIFFERENT assets (FACTS.md "Auction asset
flows"); "same logic, different request type" was the original overclaim.
Delivered scope:

| Auction type | Support | Capital | Proceeds | Evidence |
|---|---|---|---|---|
| User liquidation (0) | **FULL** — create (simulation-sized) → profitability wait → draw → ONE atomic `submit([fill, repay…, withdraw_collateral…])` → swap collateral → return | Vault draw | Measured USDC returned via `return_proceeds`; share price rose 1.0 → 1.0432672 live | docs/evidence/b-full-cycle.md |
| Bad debt (1) | **FILL-AND-HOLD** — create + atomic fill+repay from the operator float (`BAD_DEBT_MAX_SPEND` cap); free-capture past t=400; LP lot held at spot − haircut | Operator float, never vault draws | Backstop LP to the operator; profit accrues to the OPERATOR (NoDraw guard, above) | docs/evidence/c-bad-debt.md |
| Interest (2) | **DETECTED, DEFERRED** — bid requires pre-held + pre-approved backstop LP a vault-USDC keeper doesn't carry; logged once per auction, never filled | — | — | FACTS.md Decisions; `adapter.go scanBackstop` |

**Annotation — the spec's own pseudocode contains four errors the shipped
code corrects** (checklist wording must not be read as the target):

1. **Spec's `AuctionType` enum order is wrong**: it lists
   `UserLiquidation, InterestAuction, BadDebtAuction` (interest = 1). The
   contract has `BadDebtAuction = 1, InterestAuction = 2`
   (`auction.rs:19-23` @ ba22b48); the keeper matches the contract
   (`keeper/blend/auction.go:25-27`).
2. **Spec hardcodes `CreateAuction(…, 50)`** — a fixed 50% provably reverts
   `InvalidLiqTooSmall` on real positions (live probes,
   docs/evidence/b1-percent-probes.txt). Shipped: `FindLiquidationPercent`
   binary-searches with read-only `new_auction` simulations; the pool is the
   authority (FACTS.md Decisions).
3. **Spec's cycle draws BEFORE creating the auction and busy-waits inside
   Execute.** Shipped order: create → check profitability on the verified
   two-phase curve → size the draw from the auction's actual debt legs → draw
   → atomic fill. A fill alone transfers no tokens (the filler assumes dToken
   debt), so fill+repay+withdraw is ONE health-checked submit — the spec's
   separate "fill then return `needed + result.Profit`" sequence would strand
   debt between transactions and book synthesized profit. Shipped proceeds
   are MEASURED (USDC balance delta), never computed.
4. **Spec's profitability curve is the pre-verification model.** The README's
   old `lotPct = elapsed/200, bidPct = (200-elapsed)/200` (simultaneous)
   is wrong; the verified curve is two SEQUENTIAL phases over 400 ledgers
   with the fair point at t=200 (`auction.rs:189-264`; FACTS.md "Auction fill
   price curve"). The keeper implements the verified curve
   (`keeper/blend/auction.go:314-338`, tests `TestProfitability_*`,
   `TestPhaseAt_Boundaries`).
